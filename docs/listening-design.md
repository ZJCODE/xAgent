# 持续听，但不逐条排队回答

Status: implemented (v1). 飞书群 / 飞书私聊 / 微信私聊走感知环 + 注意环；
Web/API 与语音未改。说之前的陈旧复查、STEER 打断、重启回放积压仍按第 6 节推迟。

## 0. 问题

今天 agent 把"一条消息到达"等同于"一个回合"。飞书群未 @ 的消息走
`_dispatch → chat_lock → 拉飞书历史 → decide_participation → chat | observe`，
每条一次；私聊每条直接 `chat`，按 chat 加锁串行。别人连续说五句，agent 就排队做
五次"要不要接话"，后几次评估的还是已经被自己回复越过的消息；私聊里第 3 条改了
主意，第 1 条已经在回了。

`observe` 是决策为"否"之后才落地，听到不等于记住。

记忆侧没有这个问题：`schedule_experience_write` 只是触发一次带门槛的 maintenance。

## 1. 第一性原理

1. **意思以"段"为单位到达，消息只是段的切片。** 一个人的一个想法常跨几条消息；
   几个人的一段交流跨几轮。对一条消息下判断，判断的对象是错的。
2. **感知和注意是两种代价。** 记下"发生了什么"几乎免费，必须对每条消息都做，且
   不能被任何判断阻塞。"我要不要说、说什么"要调模型，必须省着用。
3. **一个 agent 一张嘴。** 同一时刻只能产生一段发言。`AgentInbox` 的轮次锁已经
   表达了这一点，但只在"正在说"时生效，"想说"阶段今天没有约束。
4. **沉默是信号。** 说话的人停下来，意思才完整。对旁听的话题，等一等是礼貌；
   对直接问我的话，只能等很短。
5. **已说的是事实，想说的是草稿。** 消息表是唯一的事实；"我打算回应什么"在说出
   之前随时可以丢弃、重算，不需要被当成对象保存。
6. **输出永远是主动的。** agent 决定在某个房间说一句话，渠道负责送达。今天定时
   任务和潜意识发言已经是这个形态；对话回复没有理由是另一种形态。

## 2. 由此推出的模型

### 2.1 两个环，用消息表连接

```
感知环（每条消息，同步，不调模型）
  渠道收到消息 → 写入消息表（含 room_key、sender、addressed_to_agent） → attention.notice(room_key, addressed)

注意环（每个 agent 一个，串行，调模型）
  等待唤醒 → 找出"未注意区间"最该看的房间 → 判断 → （说 | 不说） → 推进游标 → 回到等待
```

两环之间唯一的共享状态是消息表加每个房间的两个游标。没有 per-message task，
没有内存中的"待评估意图"队列。"合并 / 替换过时的考虑"不需要实现——因为不存在
需要被合并的对象，只存在"我上次看到哪了"。

### 2.2 每个房间两个游标

消息表已有单调 `cursor`（`get_latest_message_cursor`）。每个房间记：

```
attended_through   # 我最后一次形成判断时，该房间的 cursor
spoken_through     # 我最后一次在该房间发言时，该房间的 cursor
```

未注意区间 = `(attended_through, latest]`。这就是"当前情境"的全部定义。
它由消息表实时给出，不用维护 `burst` 缓冲。判断所需的更早历史也从消息表按
`room_key` 读。

游标是运行态，存在 `messages/` 下一个小 json 里（与 `WorkingContextStore` 同级
的一次性文件）。丢了就重建：重启时 `attended_through = latest`，不回放积压。

### 2.3 唤醒策略：什么时候看

全部是计时器与计数，不调模型。对每个有未注意区间的房间：

| 条件 | 触发 |
| --- | --- |
| 区间里有直接给我的话 | 短宽限（接住"哦对了还有…"）后立刻 |
| 房间安静了 T 秒 | 安静即看 |
| 区间超过 K 条 | 不等安静 |
| 区间最早一条超过 M 秒 | 不再等 |

多个房间同时到期：有直接给我的话的优先，其次等得最久的。

初始值只是起点，要靠日志调：直接给我的宽限约 1 秒，安静窗口约 3–5 秒，
K 约 12，M 约 20 秒。

### 2.4 一张嘴

注意环本身就是串行的，天然满足"同时最多一个发言意图"。判断和发言期间到达的
消息只是让 `latest` 前进；这一轮结束后回到等待，下一轮自然看见它们——连同
自己刚说的那句。

### 2.5 判断的输入是区间，不是消息

`decide_participation` 的输入从"这一条 + 历史"改为"未注意区间 + 之前的房间
历史（含我上次说过什么）"。输出保留 `should_reply / reason`，增加 `addressing`
（区间内我在回应哪几条）。

回复回合的输入同样是区间。这需要一个新的核心原语：

```
agent.respond(room_key, through_cursor)
```

它和今天的 `chat_events` 走同一条 `_drive_claimed_turn`，区别只在"用户消息"
不是新传入的 payload，而是消息表里 `(attended_through, through_cursor]` 这段
已经存在的记录。这是整个方案里唯一真正的架构改动：**回合的输入是消息表中的一段
游标范围，而不是一条消息**。其余都是它的推论。

### 2.6 所有输出都是送达

`respond` 产出的文本通过渠道的送达接口发到 `room_key`，与定时任务、潜意识发言
使用同一条 push 路径（飞书今天的 `_dispatch_scheduled_task` 那条）。飞书需要的
`reply_to` 锚点（话题群）用区间里最后一条被 `addressing` 的消息。

入站消息不再"拥有"一个回复。渠道 adapter 的职责收缩为两件事：把到达的消息写进
消息表并 `notice`；把 agent 要说的话送到房间。

## 3. 直接给我的话

不做成单独对象。它是区间里某些消息的一个属性（`addressed_to_agent`，飞书群的
观察元数据里今天已经有）。三条规则让"单独保留"成立：

1. 区间里有直接给我的话时，唤醒走短宽限，不等安静窗口。
2. 判断不允许对含直接给我的话的区间返回"不说"（今天 @ 必回，规则不变）。
3. `attended_through` 只在这一轮结束时推进。如果回合失败，游标不动，这些话留在
   区间里，下一轮再看。

同一个人在一波里的几条直接提问，在一个回合里一起答——这就是"保留"和"逐条"
的区别。

## 4. 各渠道如何映射

| 渠道 | 房间 | 每条是否直接给我 | 变化 |
| --- | --- | --- | --- |
| 飞书群 / 话题群 | `feishu:<chat_id>` | @ 我 / 回复我 → 是；否则否 | 先写表再 notice；判断按区间；飞书历史 API 只在本地表有缺口时补一次 |
| 飞书私聊 | `feishu:<chat_id>` | 是 | 不再逐条 chat；短宽限合并后一个回合 |
| 微信私聊 | `weixin:<user_id>` | 是 | 同上 |
| 语音 | 1:1 | 是 | 不变。Soniox 端点检测已经在音频层做了"等说完" |
| Web / API | 请求方等待响应 | 是 | 不变。这是 pull 介质，客户端在等这一次响应，合并没有意义 |
| 定时 / 潜意识 | 目标房间 | — | 不变，已经是 push；成为 `respond` 输出的同路 |

Web/API 保留 `chat_events` 原样。本方案只改 push 介质。

## 5. 需要的改动（清单）

- **消息表**：按 `room_key + cursor 范围` 读；写入时保证 `room_key`、
  `addressed_to_agent` 可查。纯读取增加，不引入新存储。
- **核心** `xagent/core/attention.py`：游标持久化、唤醒策略、注意环、
  `notice()`。与 `inbox.py` 并列；`AgentInbox` 继续做最后一道锁。
- **核心** `agent.respond(room_key, through_cursor)`：复用 `_drive_claimed_turn`，
  输入来自消息表区间。
- **核心** `decide_participation`：接受区间形状的输入；返回 `addressing`。
- **飞书 adapter**：`_route` 的群分支与 p2p 分支都改为"写表 + notice"；
  `_handle_chat` 的回复发送部分抽成送达接口，供 `respond` 输出调用；
  `_fetch_group_history` 降级为补洞。
- **微信 adapter**：`_handle_dm` 改为"写表 + notice"；送达接口复用现有发送。

## 6. 明确不在第一版做的

- **说之前的陈旧复查。** 判断覆盖到 N，说出来时房间已经到 N'。第一版不复查：
  下一轮会连同我的发言一起看到 (N, N']，需要补的自然补。人也是这样说话的。
  只有"别人已经替我答了"这一种情况会多说一句，用指标看它有多常见再决定。
- **区间里直接给我的话被回复遗漏的兜底。** `addressing` 让它可观测，先观测。
- **说话中被打断。** `InboxKind.STEER` 与 `AgentInbox.request_abort()` 已存在
  未用，是将来的入口，不是现在。
- **重启回放积压。** 游标重置到 `latest`。

## 7. 落地顺序

每步可独立合入、独立验证。

1. **消息表按房间读 + 飞书群先写表再 notice。** 已落地。
2. **`attention.py` + `respond`。** 已落地。飞书群与私聊切到 notice；真实 Agent 用 `respond` 读区间，测试假 Agent 仍走原来的 `chat_events` 发送。
3. **微信私聊接入。** 已落地。
4. 视指标决定是否做第 6 节里的项目。

## 8. 指标（第 1 步起记日志）

- 每条群消息触发的判断次数（目标一波内 ≪ 1）
- 每波的回复条数（目标 ≤ 1）
- 直接给我的话与私聊从到达到首字的延迟（上限要定死，不能明显比今天差）
- 回应了已被别人回答的消息的次数（决定要不要做陈旧复查）
- 区间含直接给我的话、但 `addressing` 未覆盖它的次数（决定要不要做遗漏兜底）

## 9. GOAL.md check

- **Identity** — 一个注意环 = 一张嘴；不改 persona。
- **Multi-user** — 游标按房间，消息带 sender；判断输入里每条话都有归属。
- **1:1 and group** — 同一个环，私聊是"每条都直接给我"的房间。
- **Memory / journal** — 感知环先写表，日记仍是唯一记忆载体；沉默从每条一条
  变为每区间一条。
- **Unified memory** — 无按用户切分的新存储；游标文件是可丢弃运行态。
- **Sharing** — 说不说、说什么仍由 agent 判断，只是对象从一句变成一段。
- **Diary-anchored** — 游标可从消息表重建，不是第二个真相源。
- **Attribution / continuity** — 判断和回复都以 cursor 区间为锚；`addressing`
  让每次发言能追溯到回应的是哪几句。
- **Environment-aware** — 一切先作为观察进入，直接请求由 `addressed_to_agent`
  显式区分，不靠推断。
